# .NET 10 package modernization and API adoption

This change bumps all NuGet dependencies to their latest stable versions (EF Core 10.0.8, ASP.NET Core 10.0.8, OpenIddict 7.5.0, FluentMigrator 8.0.1, StackExchange.Redis 2.13.17, etc.), removes two obsolete package references, and introduces three code-level modernizations: the `Check` utility delegates to framework guard methods, `MimeTypeMap` uses `FrozenDictionary` for read-hot lookups, and new `TimeProvider`-based `IClockProvider` implementations are available alongside the existing ones. The FluentMigrator 7.x to 8.x jump required adapting `VersionTable` to the new constructor signature, which removes the parameterless constructor — a breaking change for any downstream code that instantiates it directly.

**Watch for:** Inconsistent version bumps leave some Microsoft packages at 10.0.0 while peers are at 10.0.8 (confirmed). The `Check` modernization changes exception message formats, which could break tests or log-parsing that expects specific strings (confirmed). The `TimeProviderClockProvider` constructors are public but there's no null-guard on the injected `TimeProvider` (confirmed).

## High-level view

The package version sweep is thorough for the packages it touches but incomplete — `Microsoft.EntityFrameworkCore.SqlServer`, `Microsoft.EntityFrameworkCore.Design`, `Microsoft.EntityFrameworkCore.Tools`, `Microsoft.AspNetCore.Mvc.Testing`, and the `System.DirectoryServices.*` packages in `Abp.Zero.Ldap` remain at 10.0.0 while their siblings move to 10.0.8. These are all in test/sample projects and one source project, so the mismatch creates a diamond-dependency risk where runtime binding redirects may silently resolve version conflicts.

The `Check.cs` refactoring is a behavioral change disguised as a mechanical one. The previous code threw `ArgumentException` with a message like `"paramName can not be null or empty!"`, while `ArgumentException.ThrowIfNullOrEmpty` produces the framework's default message format (`"The value cannot be an empty string. (Parameter 'paramName')"`) and additionally throws `ArgumentNullException` instead of `ArgumentException` for null inputs. Any code asserting on specific exception types or messages will break.

The `FrozenDictionary` adoption in `MimeTypeMap` is well-executed — the mutable fallback path only materializes when `AddMimeType`/`RemoveMimeType`/`AddExtension`/`RemoveExtension` are called, so the common read-only path benefits from the optimized lookup. The one gap is that mutations through the mutable dictionary are invisible to prior frozen snapshots, but since `MimeTypeMap` is registered as `ITransientDependency`, each consumer gets its own instance and this is unlikely to cause shared-state issues.

The `TimeProvider`-based clock providers are additive and non-breaking. They wire `TimeProvider.System` into static instances on `ClockProviders`, making the new .NET 8+ time abstraction available through ABP's clock system without changing the default behavior.

The FluentMigrator 8.x upgrade removes the parameterless and single-string constructors from `DefaultVersionTableMetaData`, requiring `VersionTable` to accept `IConventionSet` and `IOptions<RunnerOptions>` via DI. This is a breaking change for anyone instantiating `VersionTable` manually outside of DI.

1. **Inconsistent Microsoft package versions** — Several Microsoft packages remain at 10.0.0 (SqlServer, Design, Tools, Mvc.Testing, DirectoryServices) while their peers are at 10.0.8. Bump them all to 10.0.8 or document the intentional exclusion.

4. **VersionTable breaking change undocumented** — The removal of the parameterless constructor in `VersionTable` is a binary-breaking change for consumers using FluentMigrator outside DI. Add a note to the upgrade summary or migration guide.
5. **MimeTypeMap mutation doesn't invalidate frozen dictionary** — After `AddMimeType`/`RemoveMimeType` is called, read methods check `_mutableMappings != null` to route reads. But if `TryGetMimeType` is called on one thread while another calls `AddMimeType` for the first time, the `_mutableMappings` field assignment lacks synchronization. Since `MimeTypeMap` is transient, this is only a concern if a single instance is shared across threads, which the DI registration makes unlikely — but worth documenting the non-thread-safe mutation contract.

## Exception behavior change in Check.cs

The original `Check.NotNullOrEmpty` threw `ArgumentException` for both null and empty inputs with the message `"{paramName} can not be null or empty!"`. The new implementation splits behavior: `ArgumentException.ThrowIfNullOrEmpty` throws `ArgumentNullException` when `value` is null, and `ArgumentException` with a different message when it's empty. The same split applies to `NotNullOrWhiteSpace`.

```csharp
// Old: always ArgumentException
throw new ArgumentException($"{parameterName} can not be null or empty!", parameterName);

// New: ArgumentNullException for null, ArgumentException for empty
ArgumentException.ThrowIfNullOrEmpty(value, parameterName);
```

This is observable in catch blocks that discriminate on exception type, and in tests that assert `Assert.Throws<ArgumentException>(() => Check.NotNullOrEmpty(null, "x"))` — those will now fail because the thrown type is `ArgumentNullException`. The `using Abp.Extensions` removal is correct since the `IsNullOrEmpty()` / `IsNullOrWhiteSpace()` extension methods are no longer called, but the `using Abp.Collections.Extensions` remains because `NotNullOrEmpty<T>(ICollection<T>)` still uses `IsNullOrEmpty()` on collections.

## TimeProvider clock providers — constructor safety

Both `TimeProviderClockProvider` and `UtcTimeProviderClockProvider` store the `TimeProvider` parameter without validation:

```csharp
public TimeProviderClockProvider(TimeProvider timeProvider)
{
    _timeProvider = timeProvider;  // no null check
}
```

Since these types have public constructors (unlike `LocalClockProvider` and `UtcClockProvider` which are `internal`), consumers can instantiate them with arbitrary `TimeProvider` instances, including null. Adding `ArgumentNullException.ThrowIfNull(timeProvider)` would be consistent with the Check.cs modernization and fail fast.

The `SupportsMultipleTimezone` property returns `true` on both new providers, diverging from `LocalClockProvider` which returns `false`. The distinction is intentional — `TimeProvider` can be configured with arbitrary time zones — but it means swapping `ClockProviders.Local` for `ClockProviders.TimeProviderLocal` changes the `SupportsMultipleTimezone` contract, which ABP uses to decide whether to store timezone info alongside `DateTime` values.

## FrozenDictionary in MimeTypeMap

The implementation creates the `FrozenDictionary` in `BuildMappings()` by calling `.ToFrozenDictionary(mappings.Comparer)` at the end, preserving the case-insensitive comparer. Read methods (`TryGetMimeType`, `TryGetExtension`) check `_mutableMappings != null` before falling through to the frozen dictionary, which routes to the mutable copy once any mutation has occurred.

The `GetMutableMappings()` method lazily copies the frozen dictionary into a regular `Dictionary<string, string>`:

```csharp
private Dictionary<string, string> GetMutableMappings()
{
    if (_mutableMappings == null)
    {
        _mutableMappings = MappingDictionary.Value.ToDictionary(
            kvp => kvp.Key,
            kvp => kvp.Value,
            MappingDictionary.Value.Comparer);
    }
    return _mutableMappings;
}
```

This is not thread-safe — two concurrent calls to `AddMimeType` could race on the null check. Given the `ITransientDependency` registration (each injection site gets its own instance), multi-threaded mutation is unlikely but not impossible if the instance is captured and shared. The previous `Dictionary` implementation had the same limitation, so this isn't a regression, but it's worth noting since `FrozenDictionary`'s name might imply thread-safety guarantees that the mutable fallback doesn't provide.

## FluentMigrator 8.x breaking change in VersionTable

FluentMigrator 8.0.1 removes the obsolete parameterless and `string`-accepting constructors from `DefaultVersionTableMetaData`. The updated `VersionTable` now requires `IConventionSet` and `IOptions<RunnerOptions>` through dependency injection:

```csharp
public VersionTable(IConventionSet conventionSet, IOptions<RunnerOptions> runnerOptions)
    : base(conventionSet, runnerOptions)
```

This only works when `VersionTable` is resolved through DI (which is the normal FluentMigrator runner path). Any code that was `new VersionTable()` or `new VersionTable("schema")` directly — unlikely in production but possible in tests — will fail at compile time.

## Incomplete version sweep

The diff updates Microsoft packages to 10.0.8 in most projects but leaves others at 10.0.0. These are pre-existing values that weren't touched:

- `Abp.ZeroCore.SampleApp`: EF Core Design, SqlServer, Tools at 10.0.0
- `AbpAspNetCoreDemo`: EF Core SqlServer at 10.0.0
- `AbpAspNetCoreDemo.IntegrationTests`: Mvc.Testing at 10.0.0
- `Abp.Zero.Ldap`: DirectoryServices packages at 10.0.0

Within the demo project `AbpAspNetCoreDemo.csproj`, EF Core Sqlite is bumped to 10.0.8 while SqlServer remains at 10.0.0 in the same file — this was partially touched by the change, creating an inconsistency within a single project file.
